# face 콕 — 보안/비밀값 관리 체크리스트

정리 기준일: 2026-09-03

이 문서는 레포에 올리면 안 되는 값과 비밀값 관리 원칙을 정리한다. 실제 비밀값(키,
비밀번호, 토큰)은 이 문서에 절대 적지 않는다 — 변수 이름과 규칙만 다룬다.

## 1. 절대 커밋하면 안 되는 파일

| 파일/패턴 | 담긴 것 | 보관 위치 |
| --- | --- | --- |
| `.env`, `.env.local`, `.env.*` | DB 접속정보, 세션 시크릿, SMTP 계정, VAPID 키 | 각자 로컬만 |
| `application-local.yml` | 로컬 전용 스프링 설정 | 각자 로컬만 |
| `*.pem`, `*.key` | 인증서, 개인키 | 저장소 폴더 밖 |
| AWS 자격증명 파일(`~/.aws/credentials` 등) | AWS Access Key/Secret Key | 저장소에 절대 두지 않음 |

`.env.example`만 저장소에 공유하고, 변수 이름과 안전한 더미값(또는 빈 값)만 담는다.
백엔드 레포 생성 시 `.gitignore`에 위 패턴이 전부 들어있는지 최초 커밋 전에 확인한다.

## 2. 로컬 값 vs 운영 값 분리

- **로컬 개발용 값**: [온보딩.md](./온보딩.md) 6번 표의 값(팀 내부 공유, 운영 값과
  다르게 설정). 각자 로컬 `.env`/`application-local.yml`에만 존재
- **운영(AWS) 값**: **AWS Secrets Manager**에서만 관리한다. 문서·코드·CI 설정
  어디에도 하드코딩하지 않는다
- 로컬 값과 운영 값은 반드시 다른 값을 쓴다 — 같은 `SESSION_SECRET`을 로컬·운영에
  같이 쓰면 로컬 유출이 곧 운영 유출이 된다

## 3. 관리 대상 비밀값 목록 (변수명만, 값은 미기재)

| 변수 | 용도 | 비고 |
| --- | --- | --- |
| `DB_USERNAME`, `DB_PASSWORD` | RDS MySQL 접속 | 로컬/운영 분리 |
| `SESSION_SECRET` | 세션 쿠키 서명(HMAC) | 유출 시 세션 위조 가능 — 최우선 보호 대상 |
| `SMTP_USER`, `SMTP_PASS` | Brevo 이메일 인증코드 발송 | 유출 시 스팸 발송 악용 가능 |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` | 웹 푸시 인증 | PRIVATE_KEY만 비밀, PUBLIC_KEY는 클라이언트에 노출되는 게 정상 |
| 관리자 로그인 비밀번호(해시) | `/api/auth/admin-login` | 평문 저장 금지, 해시만 DB에 저장 |
| AWS Access Key / Secret Key | 인프라 배포·Secrets Manager 접근 | 개인 계정 자격증명, 코드에 절대 미포함 |

## 4. 세션/인증 관련 보안 원칙

- 세션 쿠키는 **HttpOnly** — 자바스크립트로 접근 불가하게 해서 XSS로 인한 쿠키 탈취 방지
- 세션 쿠키는 **서명(HMAC)** 되어 있어 클라이언트가 값을 조작해도 서버가 위조를 감지
- 참가자 세션과 관리자 세션은 **분리**된 세션으로 관리([기능명세.md](./기능명세.md) 1번) — 관리자 권한이 참가자 세션 위조로 뚫리지 않게 함
- 정지된 계정은 로그인 시도 시 즉시 차단하고, **이미 로그인된 세션도 요청마다 상태를
  재확인**해서 정지 감지 시 강제 로그아웃한다([기능명세.md](./기능명세.md) 1번) —
  세션 발급 이후 계정이 정지돼도 즉시 반영되게 하는 장치

## 5. 인프라 보안 원칙 (요약, 상세는 [인프라설계.md](./인프라설계.md))

- EC2는 Public Subnet에 두되, **인바운드는 ALB Security Group으로만 제한** (NAT Gateway 미사용)
- RDS는 EC2 보안그룹에서만 접근 가능하게 제한 (외부 공개 금지)
- 개인정보처리방침에 동의한 참가자 이메일 등 개인정보가 DB에 저장되므로, RDS 접근
  권한은 필요한 사람만 부여
- Supabase(Postgres)를 쓰던 시기 RLS/anon key 노출 문제가 있었던 이력이 있어
  AWS RDS 전환 후에도 **DB 자격증명 노출 여부를 재점검**한다

## 6. 유출 시 대응 절차 (원칙만, 상세 런북은 별도 문서 예정)

1. 유출된 값을 즉시 **재발급/폐기**하고 운영 환경에 반영
2. 재발급 전에 **영향 범위 확인** (해당 키로 접근 가능했던 리소스가 무엇인지)
3. 팀 전체가 같은 값을 공유 중이었다면 재발급 시 **사전 공지** — 갑자기 끊기면 장애로 오인될 수 있음
4. 재발급 완료 후에만 기존 값 폐기 (순서: 새 값 발급 → 동작 확인 → 기존 값 폐기)

## 7. 이번 문서 범위 밖

- 실제 `.env.example` 내용과 정확한 변수 전체 목록은 백엔드 레포 생성 시 확정
- AWS Secrets Manager 실제 연동 방식(IAM Role, 로테이션 정책)은 백엔드 인프라 붙일 때 별도 정리
- 장애 대응 런북, 침해 사고 대응 절차는 [테스트/장애대응 문서](#) 작성 시 다룸 (아직 미작성)
